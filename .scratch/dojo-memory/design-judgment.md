Choose B as the base. It preserves the UniiChat invariant that the archive is the conversation: exact user/assistant/tool history remains retrievable, while summaries are replaceable indexes. A selectively stored fact log would contradict that requirement. T3 exposes tool and command output through `turn-item.updated`, with `getTurnItem` for large items; persist those returned bytes and their completeness status rather than silently substituting previews. The promise is faithful retrieval of what T3 exposes.

B also gets routing right: a request arriving during an active run steers that thread; after terminal state, the next request gets a fresh thread with a frozen view. This fits Dojo’s present conversation behavior and avoids treating timing alone as a new request.

Keep the essential isolation: create one dedicated T3 project with `projects.create`, deterministic ID, title, workspace root, and explicit data directory/agent workspace. Put Dojo’s instructions and MCP config there only. For non-scratch roots, account for `thread.worktreePath` being null by using the known workspace root. Leave T3 defaults, global instructions, unrelated threads, and shared scratch files alone.

Trim B’s machinery to the smallest proof: durable per-record files plus append log, atomic saved view, one writer, idempotent `open/append/view/zoom/date/search/work` API. Use an event-driven worker with one summary task only when idle; no eight-call fan-out or polling. Prove two live requests: first records a distinctive fact, second starts fresh and retrieves its exact source; verify dedicated workspace and an unrelated thread unchanged. Keep recovery and pagination needed for durable, faithful retrieval.
