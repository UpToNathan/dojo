# Dojo capture and CUA integration: architectural grounding

This describes the implementation at the adoption result's pinned source state (`88aff7e5424e9ed45b93ded85eb4111472ca5190`) and distinguishes it from the still-proposed adoption roadmap. The source notes are `/tmp/dojo-cua-ground-native.md` and `/tmp/dojo-cua-ground-semantic.md`; current implementation evidence and remaining gates are recorded in `.scratch/cua-adoption/result.md`, against `.scratch/cua-adoption/spec.md`.

## Overview

The current desktop path has a clear authority split: `dojo-computer` owns capture identity and admission; the shared `dojo-agent` service owns per-client sessions and native input controllers; Niri owns final input delivery and checks the target at dispatch; Pi owns the durable conversation, tool scheduling, and recovery state. A screenshot is evidence tied to a session and geometry, not authorization by itself. Native actions consume that evidence before effects and require a new observation afterward.

CUA's native capture, AT-SPI, and browser implementations are candidate Rust capabilities to bring behind this existing Dojo authority. They are not yet one integrated runtime. The pure model-output parser library is ported, but is not wired as an executing provider bridge. Semantic and browser reads/mutations, native Wayland capture, and the broader CUA roadmap remain future work.

## Current capture and action flow

`desktop_observe` enters `Session::observe` in `src/bin/dojo-agent/service.rs`. The service validates the requested scope and cancellation state, reads a live `CaptureFrame`, captures with grim, reads the frame again, and rejects if the frames differ. It then publishes image bytes, dimensions, digest, and mapping into the session's `CaptureSession`. Observation creates no input seat. The older `desktop_screenshot` route remains a direct capture path and does not provide the same capture-bound action contract. See `service.rs` observation/action methods and `src/bin/dojo-agent/screenshot.rs` capture planning.

Capture identity is more than an image rectangle. `crates/dojo-computer/src/lib.rs` represents a `WindowIdentity` with Niri window ID, PID, process start time, optional app ID, and workspace; `OutputFrame` carries named output, global origin, logical dimensions, scale, and transform; `CaptureFrame` adds the output-relative integer crop and input-coordination revision. This blocks PID reuse and catches output/workspace/geometry/coordination changes that invalidate an observation.

Screenshot planning resolves the requested output and optional region or positioned window. Window scope currently depends on Niri's active workspace and `tile_pos_in_workspace_view`; the crop includes tile decorations. Grim captures at the requested scale. The delivered PNG's actual dimensions drive independent x/y pixel-to-logical mapping, so callers act in delivered-image coordinates rather than assuming nominal scale. Crops are bounded by dimension, pixel, and encoded-byte limits. A crop may contain occluding content; only a positioned-window capture has the identity required for guarded effects. Full-output and region captures are read-only for capture-bound actions.

`desktop_capture_action` asks the service to resolve the stored capture and compare it to the live frame, then `CaptureSession::admit` checks session binding, validity/TTL, frame and target identity, and mapped coordinates. Admission consumes the capture and retires sibling observations before any possible effect. The service lazily creates an independent input controller, moves to the mapped location, waits for arrival, and rechecks geometry, target identity, and coordination revision before dispatch. A successful response means input was handled, not that the user's task succeeded (`verified: false`); another observation is required. Failures can be unknown because the external effect may have occurred.

The Niri client wrapper carries coordination revision and exact window target to dispatch. Niri rechecks coordination, hit-tests the current pointer content (including popup/subsurface ancestry), verifies the mapped toplevel target, and checks human application ownership before delivering press/key/axis effects. Cleanup releases are allowed without target matching. IPC transport failure closes the controller because a late response cannot safely be attributed to a later effect. These checks secure Niri-delivered input; they do not automatically secure CDP or D-Bus effects.

## Pi and durable ownership

`tools/speech/desktop-extension.mjs` registers the named `dojo-desktop` extension, pins its schema/catalog fingerprint, and routes tools through the MCP subprocess. `tools/speech/pi-runtime.mjs` executes tools sequentially, classifies effects as unsafe to replay, persists capture-consumption/recovery state before dispatch, and invalidates capture history on session changes. Stop, abort, or client loss closes the MCP process so its Rust service can release the seat and settle pending work. The durable Pi tool result and memory path preserve returned images. A new client session must observe again.

The ownership boundary is deliberate: Pi/pi-durable remains the only scheduler, transcript, and task persistence owner; `pi-ai` remains model transport/credentials/streaming owner; Rust owns desktop execution, observation state, parsing/normalization, and eventual policy. The adoption document describes this target; only the desktop capture/action lifecycle and pure model decoder are evidenced as implemented slices. No exactly-once guarantee exists across the crash window between an external UI effect and recording its result. Recovery must not replay ambiguous actions.

## Where CUA capabilities fit

### Native Wayland capture and geometry

Current capture uses grim. CUA's `platform-linux/src/wayland/ext_screencopy.rs` is a Rust client for standard output capture, but it is not adopted. Niri already implements the standard capture protocol in `vendor/niri/src/handlers/image_copy_capture.rs` and renders through `Niri::render_for_image_copy_capture`. The smallest sensible integration seam is a Rust platform backend under the existing `dojo-computer` scope/session owner: take an already resolved named-output plan plus deadline/cancellation, return delivered bytes/dimensions and actual format/transform metadata, then apply the same crop and coordinate contract as grim.

Native capture alone does not solve window capture. Stable Niri IPC `WindowLayout` is not render-time geometry: tiled positions are not populated, floating IPC omits render offsets, and animations, overview, clipping, and workspace transitions alter what is drawn. A future compositor observation must provide mapped window identity plus rendered bounds/clip/visibility and correlate that scene evidence with the captured frame, or refuse unsupported transition states. Separate Outputs/Windows/Workspaces reads and before/after equality catch many changes but are not atomic with pixels. Standard screencopy presentation time is a possible join key, not a guarantee that Niri window geometry is exported with it.

CUA's current native client also needs correctness work before reuse: it selects the first output, ignores frame transform/presentation metadata and lifecycle events, assumes pixel format/stride, uses blocking roundtrips that deadlines cannot interrupt, and manually manages SHM resources without full error-path RAII. Output identity must be explicit; unsupported formats/transforms and resource bounds must be handled. These are integration constraints, not claims that Dojo already has native capture.

### AT-SPI semantic observation

CUA desktop accessibility has its own `SnapshotStore`, retained payloads, `ResolvedElement`, and `sXXXXXXXX:index` tokens. Linux walking gathers a bounded tree, bounds, trust/scope/truncation evidence, and retains native element references; later actions resolve the retained object instead of re-walking an ordinal. That is the useful semantic pattern: observe once, retain identity, and execute against that identity.

There are material token ownership weaknesses to fix before exposure. Upstream `SnapshotStore::resolve(pid, ...)` checks snapshot/window/element membership but does not enforce screenshot owner or Dojo session ownership. A process-global AT-SPI side index can return the first snapshot for a PID when xid is absent. Bare row numbers can resolve against a current unambiguous window; token counters restart at one. Thus a token string is not sufficient proof of current session, process generation, or observation. Dojo must bind semantic references to server-owned session identity, runtime epoch, exact window/process identity, and retained observation; reject publication after teardown; and remove ambiguous PID/row fallbacks from action paths. AT-SPI action entrypoints are direct D-Bus effects, so hiding action tool names does not itself make a backend read-only.

AT-SPI tree observations can remain useful when window correlation is not proven, but they must be marked unscoped/non-actionable. Replacing CUA's Niri/Wayland identity discovery with Dojo's exact Niri evidence is an adapter task, not an already established mapping—especially for correlating an AT-SPI frame in a multi-window process.

### Browser observation and control

CUA's browser subsystem is a separate implementation from desktop AT-SPI: `BrowserEngine` owns `BrowserStore`, CDP connections, browser preparation/grants, mutation/reconnect gates, cleanup and policy-related dependencies. Browser refs (`p<snapshot>:index`) bind to session, target, tab, frame/document, and endpoint generation; navigation/new snapshots invalidate old refs. Before mutation it revalidates process/endpoint ownership, exact native-window geometry/cardinality, CDP target and URL scope, then separately checks frame/document identity. This is a coherent reusable engine, not just a collection of DOM helpers.

Those checks establish target identity and serialize CUA agents, but do not establish priority over human activity. Every CDP or AT-SPI mutation—including navigation, typing, dialogs, file operations, downloads, setup, and consent effects—needs Dojo's enforceable admission/takeover semantics. Reading coordination revision and then making a CDP/D-Bus call is not equivalent to Niri's check-at-dispatch wrapper. Browser semantic mutation must remain unavailable until that admission path is designed and proved. Browser setup/grants also need to live under Dojo session lifecycle and explicit authorization, not an independent CUA runtime.

## Current versus planned

Implemented at the reported source state: shared Rust capture authority/session references; grim-backed `desktop_observe`; capture-bound guarded native action with consume-before-effect admission; Niri target/coordination checks; Pi durable desktop registration, unsafe replay classification, recovery and process teardown; and pure Rust CUA model-output decoders. The reported live integration drove a real MCP subprocess and Pi durable scheduler in a nested compositor with a scripted provider and checked client-owned events, focus, replay/session refusal, geometry changes, takeover, occlusion, release, and abrupt MCP loss. It did not use a real provider or install/restart the desktop compositor. That evidence supports the bounded slice, not all CUA parity.

Still planned or gated: native screencopy backend and trustworthy capture-correlated window geometry; AT-SPI runtime integration and session-bound semantic tokens; browser engine integration and admission for external mutations; full receipt/contract parity, recovery/version migration, broader capture matrix; provider execution of the Rust model decoders; and later verification, recording, benchmark, policy, and model-inference capabilities. The source notes describe candidate boundaries and risks, not shipped behavior. The adoption roadmap remains unfinished, as `.scratch/cua-adoption/result.md` states.
