# Bluetooth design verdict

**Base: Sol’s dedicated-panel design, with a small implementation scope.** Its strongest reason is authentication: Dojo’s frame has no keyboard input. PIN/passkey entry inside Luna’s inline panel would require changing the frame’s input policy and coordinating keyboard focus with tray, speech, and outside-dismissal handling. Sol gives pairing a keyboard-capable surface while preserving the existing frame’s input passthrough. Keep the visual prototype at `.scratch/bluetooth-controls/experience-prototype.html` as the guide for the eventual compact top-bar control and panel; this architecture does not settle its visual design.

Both candidates have a transport-free caller API and keep D-Bus details behind a process-wide controller/handle. Sol’s snapshot makes per-adapter and per-device operation state explicit, while epoch-tagged IDs reject stale commands after BlueZ restarts. Retain that shape. Luna’s simpler typed snapshot is also sound, but one global pending/error slot can hide simultaneous work across adapters and devices.

Sol is stronger on event-loop responsiveness and lifetime correctness: one actor owns the model, slow calls complete through actor messages, authentication handlers await independent replies, scan demand is represented by cancellable leases, and shutdown has an independent channel. Its ownership rule avoids stopping discovery started by another application. Graft Luna’s bounded reconnect-and-resume behavior for scans only if it can preserve that ownership rule; otherwise restart with no active scan after daemon loss. Do not adopt Luna’s per-adapter deadline scheme as a second scan model.

Retain explicit unavailable state and best-effort agent/default-agent behavior. Pairing answers must be validated and rejected on timeout, cancellation, daemon loss, and shutdown. Do not silently trust devices. Sol’s broad Agent1 method list is appropriate only insofar as each method receives a defined response; avoid exposing display-only requests as interactive prompts when they need no user decision.

The principal cost is Sol’s second layer-shell window, global panel/output handoff, and cleanup paths. It is justified by keyboard authentication, but implement one panel and one discovery lease first. Do not add a generic popup framework or one actor per display. Confirm Overlay keyboard focus and Escape/input restoration with the pending live-session prototype before expanding UI behavior.

For behavior verification, use Sol’s private D-Bus service fixture through the public controller and real actor. Keep the decisive cases: BlueZ absent/reappearing, authoritative property updates, failed connect/power, scan lease release without stopping another client’s discovery, pairing PIN/confirmation/rejection, daemon loss with a pending auth request, and bounded shutdown. Assert literal snapshots and recorded D-Bus calls. Hardware presence on this host is not evidence of a real BlueZ path.
