# CUA code portability into Dojo

Source snapshot: `trycua/cua` commit `88aff7e5424e9ed45b93ded85eb4111472ca5190`, read on 2026-10-12. This is a source and dependency inspection with standalone extraction tests. No full Driver runtime, downloaded models, or GUI scenarios were run. Dojo implementation files were not changed. All upstream links below are pinned to this commit.

## Adoption direction after this research

The follow-on [Rust/Pi adoption plan](../../.scratch/cua-adoption/spec.md) supersedes this report's conservative extraction order: Dojo intends broad CUA reuse, including Rust translations of useful Python behavior, while retaining pi-durable orchestration. Python adapter/package recommendations below describe technical portability, not the intended deployed architecture. See the [source-level Python port inventory](../../.scratch/cua-adoption/python-port-inventory.md) for bounded ports, provider integration gaps and deliberate corrections to unsafe/lossy upstream behavior. This report's standalone extraction evidence remains unchanged.

## What the whole system contains

CUA has two generations of client code. The current Rust SDK workspace is `libs/cua`; its Python, TypeScript, Swift, Kotlin, and browser bindings come from `cua-sdk` through UniFFI. A separate Python `cua-agent` package under `libs/python/agent` implements model loops against an interchangeable computer interface. Sandbox management is a different layer from desktop operation. The SDK can start local QEMU VMs or OCI containers, reach cloud sandboxes, or attach to direct machines. Its guest agent is `cua-spacesd`, which provides process, filesystem, desktop, accessibility, driver, media, presence, and forwarding services. Desktop actions inside that daemon call CUA Driver in process.

Spaces is the product built on this stack. It adds apps, sharing, secret/session transfer, a versioned shared drive, and persistent agents. Lume provides the macOS VM runtime. Cua Bench provides task execution and evaluation. CUA-S1 provides specialist model code. These are separately licensed and have different portability costs. [SDK architecture](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua/README.md), [daemon dependencies](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua-spacesd/crates/cua-spacesd-server/Cargo.toml).

## Small modules we can literally copy

### Terminal transcript parsing

`libs/cua/crates/cua-spaces-transcript` is the cleanest extraction. Its library accepts terminal bytes and produces screen/frame documents. It includes a terminal emulator, cast playback, Claude Code frame parser, JSON UI documents, and fixtures. Its only dependencies are `serde_json` and `thiserror`; there are no CUA runtime dependencies or platform APIs. It inherits the MIT license. Copy the crate plus its fixtures, replace workspace metadata and dependency declarations, and it can become a Dojo crate. The Claude Code parser has a particular layout profile, so terminal emulation is more generally reusable than assumptions about Claude's display. This would help if Dojo shows live agent terminals or turns terminal output into structured observations. [Exports](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua/crates/cua-spaces-transcript/src/lib.rs), [dependencies](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua/crates/cua-spaces-transcript/Cargo.toml).

### Agent detection and configuration edits

`cua-agent-setup` is MIT and has no other CUA crate dependencies. It detects coding agents, knows their MCP and skill configuration conventions, preserves JSONC/TOML formatting, backs up writes, and records reversible changes. The useful pieces are `registry.rs`, `edit.rs`, `fsutil.rs`, and the `HostEnv` abstraction. This directly applies to installing `dojo-agent` into supported agent configs. Copying the whole crate requires changing CUA names, state paths, installed server command, and bundled skill content. `skills.rs` embeds `../../skills` at compile time, so the crate cannot simply be dropped into `vendor/` without providing that directory or replacing the embed. Its dependencies include `jsonc-parser`, `toml_edit`, `serde_yaml_ng`, `include_dir`, and hashing/time crates. [Crate](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua/crates/cua-agent-setup/Cargo.toml), [implementation](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua/crates/cua-agent-setup/src/lib.rs), [skill embedding](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua/crates/cua-agent-setup/src/skills.rs).

### App icon cache

`cua-icon-cache` is MIT. It batches icon lookups, shares concurrent fetches for one key, normalizes PNGs, remembers missing icons briefly, and caps disk usage. Its keys use app identity and version rather than process ID. It depends on `cua-home` for CUA paths and write guards; otherwise it uses image, Tokio, hashing, and tracing. Copy it with `cua-home`, or replace that dependency with Dojo's cache paths. Dojo already uses image and hashing crates. This supplies cache machinery, not Linux icon discovery: callers still supply a fetch function. [Implementation](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua/crates/cua-icon-cache/src/lib.rs), [dependencies](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua/crates/cua-icon-cache/Cargo.toml).

### Tool manifest generation

`cua-spaces-contract` is MIT and depends only on schemars, serde, and serde_json. It generates the tool manifest from the same typed inputs the runtime parses. The contract also records required capabilities, error kinds, cost, transports, and result descriptions. We can copy the generator and metadata pattern for Dojo's tool contract. The supplied tool definitions describe Spaces lifecycle, volumes, accounts, and agents; copying those definitions would not implement their behavior in Dojo. [Contract](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua/crates/cua-spaces-contract/src/lib.rs), [dependencies](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua/crates/cua-spaces-contract/Cargo.toml).

## Agent loops can run on a Dojo adapter

The Python `cua-agent` package is MIT but upstream has retired it and promises no updates or fixes. Its source remains usable as an extraction or experimental dependency, with maintenance becoming ours. The current recommended route is coding agents using Driver MCP or the SDK agent runtime. [Retirement notice](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/README.md#deprecated-packages). It has an explicit `AsyncComputerHandler` protocol. It asks for environment, dimensions, base64 screenshot, click/double-click, scroll, typing, move, keypress, drag, mouse down/up, wait, and browser URL. `CustomComputerHandler` already accepts a dictionary of synchronous or asynchronous functions and handles image conversion. `ComputerAgent` accepts that protocol, so a Python adapter can route its actions to the persistent Dojo controller while using CUA's model loops unchanged. This route does not require CUA Driver, Spaces, or a VM. [Protocol](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/python/agent/cua_agent/computers/base.py), [callback adapter](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/python/agent/cua_agent/computers/custom.py), [agent](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/python/agent/cua_agent/agent.py).

The concrete work is coordinate mapping between the screenshot and the targeted Dojo window, key/button conversion, held-input cleanup, and handling human ownership pauses. The protocol describes desktop actions and has no controller identity, revision token, or human handoff field. Those must stay in the Dojo adapter. Drag and browser URL require an explicit supported implementation or a refusal; a model loop that asks for them cannot be declared fully compatible from the protocol match alone. Choose a loop/action set Dojo can actually deliver.

This package requires Python 3.11 through 3.13, `cua-core`, LiteLLM pinned to 1.86.2, Pydantic, Pillow, and HTTP clients. The computer/sandbox dependency is optional. Individual loop modules support OpenAI, Anthropic, Gemini, UI-TARS, Qwen, and others, but local model extras add Torch/Transformers or MLX. The source is reusable, though adding the package is a much cleaner first experiment than transplanting all of its Python internals. [Package metadata](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/python/agent/pyproject.toml).

## Larger MIT components that need a reason to import

`cua-vmm` is a genuinely separate MIT crate with no internal runtime dependencies. It supports QEMU, OCI containers through Bollard, Lume HTTP calls, and optional VNC screenshots. It is reusable on Linux for creating disposable desktops, but it solves sandbox lifecycle rather than operating the existing Niri desktop. QEMU/container execution also requires the host runtime and image handling. Dojo would need this if it adds disposable agent machines. [Runtime crate](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua/crates/cua-vmm/Cargo.toml).

The complete `cua-sdk` brings generated protobuf clients, sandbox state, images, Fleet, authentication, agent setup, daemon clients, and UniFFI exports. Its API can be used by a separate service, but vendoring it introduces a second runtime and CUA-specific state/configuration. The Rust workspace declares Rust 1.97 and UniFFI 0.31.0. Many crates use workspace metadata and path dependencies, and are `publish = false`; literal extraction needs manifests and a transitive dependency audit. The SDK's sandbox layer is intentionally independent of spacesd, so VM lifecycle can be reused even when Dojo supplies desktop input. [SDK dependencies](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua/crates/cua-sdk/Cargo.toml), [workspace](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua/Cargo.toml).

`cua-agents` normalizes coding agent installs, runs, interruptions, follow-ups, and events. It is MIT, but expects processes and files through `cua-spacesd-client` and generated protobuf types. It is not a standalone local process supervisor for Dojo. The reusable ACP event handling would require extracting transport assumptions, while its complete functionality needs a compatible daemon. [Crate](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua/crates/cua-agents/Cargo.toml).

Lume cannot become Dojo's local Linux VM engine. Its Swift package requires macOS 14 and its VM code uses Apple's Virtualization framework. It remains usable as a remote macOS host reached through the CUA SDK, but that is connecting to a runtime, not porting its implementation into Niri. [Package](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/lume/Package.swift).

## Evaluation and specialist models

`libs/cua-bench` is MIT and has an explicit Python `DesktopSession` protocol and `BaseAgent` interface. A Dojo session adapter is plausible for screenshot/input-based tasks, especially if it attaches to a disposable nested Niri session. The default session is `RemoteDesktopSession`; the simulated browser provider has been removed. The runner expects task setup, lifecycle, filesystem, and evaluation behaviors beyond a click API. Many tasks assume CUA images, installed apps, or upstream OSWorld infrastructure. Reusing task evaluators and trace/result formats is easier than claiming the entire benchmark runs on Dojo. Python requirements are 3.12 through 3.13, and installation pulls `cua-sandbox`, `cua-agent`, Hugging Face datasets, Pillow, Jinja2, and HTML parsers. [Session interface](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua-bench/cua_bench/computers/base.py), [agent interface](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua-bench/cua_bench/agents/base.py), [dependencies](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua-bench/pyproject.toml).

CUA-S1 source is MIT and structurally portable Python. Nano scores candidate element/action options; the 4B versions use LoRA adapters on Qwen3.5-4B. `driver.py` is a separate model-agnostic integration, so inference can be reused with a Dojo observation/action adapter. Its execution path currently requires a complete accessibility snapshot and a snapshot ID for element actions; a screenshot-only Dojo observation cannot satisfy that contract. Core dependencies include NumPy, safetensors, and Torch. The 4B inference extra uses Transformers 5 while training extras use Transformers 4; upstream explicitly documents that the current Qwen3.5 training recipes need a compatibility update. The code license does not grant model-weight or dataset rights; inspect each downloaded artifact separately. This is a research candidate after semantic observations exist, not an immediate improvement to pointer routing. [Model integration](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua-s1/python/src/cua_s1/driver.py), [dependencies](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua-s1/python/pyproject.toml), [documented limits](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua-s1/README.md).

## License boundary for copying source

Most of CUA is MIT, but the most product-like parts are FSL-1.1-MIT. This includes Spaces apps, `cua-spacesd` and relay, app view models, Keyvault, Teleport and its bundle format, machine sealing, volumes, Spaces extensions, Chromium session storage, media protocol/transport/codec/client, viewers, and Driver Bench. The MIT SDK/protocol/client pieces remain distinct from the FSL server and streaming implementation. Root licensing text describes the boundaries; actual package metadata must be checked because a crate under the SDK workspace can still explicitly declare FSL. `cua-media-protocol` is a concrete example. [License map](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/LICENSING.md), [media metadata](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua/crates/cua-media-protocol/Cargo.toml).

FSL permits internal use and noncommercial research, with a competing-use restriction for commercial products or services. Derivatives retain its terms, and each version gains MIT rights after two years. Spaces sharing, media streaming, Keyvault, and Teleport therefore have terms that must be evaluated against Dojo's intended use and distribution. Commercial use is not automatically prohibited; the competing-use condition matters. Their implementation cannot be treated as unrestricted MIT code. MIT code requires retaining the copyright and license notice. The deprecated Python `cua-som` is AGPL-3.0 and is explicitly kept out of MIT `cua-agent` dependencies. [FSL terms](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua-spacesd/LICENSE), [agent extras](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/python/agent/pyproject.toml).

## Recommended extraction order

1. Copy the capture registry and screenshot helpers into a small Dojo observation module. This is the strongest immediate fit. Add capture-bound actions through Dojo's existing controller, preserving human ownership checks and cleanup. The copied registry is proven to build independently; the action integration still needs live verification.
2. Extract the agent configuration editor when Dojo needs automated MCP installation. It supplies preserving edits, backups, detection, and reversal without importing the desktop driver.
3. Reuse the standalone CDP transport if Dojo needs browser observations or actions. Keep process/window binding in a Dojo adapter. Transport portability does not prove browser compatibility.
4. Extract terminal transcript parsing if Dojo renders or inspects live agent terminals, and icon-cache machinery if current app icon fetches need batching or request sharing.
5. Take cursor motion/effects as an optional visual feature. Retain Dojo's movement arrival and redirection contract until a replacement proves equivalent.
6. Add AT-SPI observations and selected benchmark evaluators through adapters. These are useful larger projects. Import VM lifecycle only if disposable agent desktops become a product requirement. Treat CUA-S1 as a separate model evaluation project.

The retired Python agent loops are mechanically adaptable but duplicate Dojo's current pi-durable runtime. They are a source reference or experiment, rather than the first extraction to ship.

## Extraction proof

The transcript crate was copied into `/tmp/cua-transcript-extract/crates/cua-spaces-transcript` with unchanged source and tests. Its checked-in transcript fixtures were copied to the original relative location. The manifest alone was replaced with standalone metadata and its two direct dependencies, `serde_json = "1"` and `thiserror = "2"`. Source/test SHA-256 equality was checked for every copied file. `devenv shell -- cargo test --manifest-path /tmp/cua-transcript-extract/crates/cua-spaces-transcript/Cargo.toml` passed all 21 upstream integration tests, including fixture reproduction and semantic false-positive cases. The standalone lockfile resolved 13 packages. This proves literal portability for this crate under Dojo's current devenv toolchain, not its usefulness in a shipped Dojo UI.

Other outside-Driver candidates above were inspected through source and dependency metadata. Their compilation and live action behavior remain unverified. An action adapter needs focused verification in live Niri.

## Driver findings

### Proven direct extractions

Five Driver production modules plus the standalone motion crate build with their source unchanged outside CUA's workspace. The extraction changes manifests and creates a module root only. Source-byte equality was checked and the upstream MIT notice retained. This is a stronger portability result than the earlier interface-only review.

| Component | Literal copy boundary | Dependencies and remaining Dojo work |
| --- | --- | --- |
| `cua-cursor-motion` | Whole crate, source, fixtures, and upstream tests | No mandatory runtime dependencies; optional serde. Convert Smithay points/time to the crate's `Pt` and trajectory samples. Paint effects in Niri. |
| `capture_registry.rs` | One complete production module | image, sha2, uuid, thiserror, serde_json, anyhow. Publish existing Dojo PNGs and bind them to Dojo sessions/targets. |
| `image_utils.rs` | One complete production module | image and anyhow. Bounded image resize, encoding, PNG dimensions, and click markers. |
| `element_frame.rs` | One complete production module | serde_json. Map semantic element rectangles to screenshot pixels once semantic observations exist. |
| `window_inspection.rs` | One complete production module | serde_json. Honest browser-chrome capture coverage metadata, not an inspection engine. |
| `browser/cdp_ws.rs` | One complete production module plus `mock_cdp.rs` for tests | Tokio, tokio-tungstenite, futures-util, serde_json. Caller must prove the endpoint and process/window ownership. |

Pinned sources: [motion crate](https://github.com/trycua/cua/tree/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua-driver/rust/crates/cua-cursor-motion), [capture registry](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua-driver/rust/crates/cua-driver-core/src/capture_registry.rs), [image helpers](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua-driver/rust/crates/cua-driver-core/src/image_utils.rs), [element coordinates](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua-driver/rust/crates/cua-driver-core/src/element_frame.rs), [capture coverage](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua-driver/rust/crates/cua-driver-core/src/window_inspection.rs), [CDP transport](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua-driver/rust/crates/cua-driver-core/src/browser/cdp_ws.rs).

The capture registry is especially useful. It retains bounded immutable screenshots, distinguishes encoded image dimensions from action dimensions, stores an affine mapping, expires captures, detects target/generation mismatch, and atomically consumes a capture for an action. Its session/target identifiers can be supplied by Dojo. It does not detect a UI changing inside an unchanged window, obtain permissions, or replace Dojo's human ownership revision check. Captures and coordination protect different facts. Dojo currently returns image/logical coordinate mapping and rechecks geometry during capture, but subsequent moves/clicks do not carry a screenshot identifier. [Dojo screenshot implementation](../../src/bin/dojo-agent/screenshot.rs), [controller](../../src/agent_input.rs).

The motion crate plans sampled trajectories with optional overshoot, heading, and effects. Its notion of first arrival can precede completion of visual settling. Dojo's controller waits for a movement that ends at the target, and raw redirection preserves velocity. Taking the crate is easy; replacing Dojo's trajectory requires deciding how settling, click timing, and redirected motion should behave. Existing [motion requirements](../../.scratch/agent-cursor-motion/spec.md) remain the acceptance contract. This is why cursor motion is a real reusable component but not the highest-value immediate import.

The CDP transport is a self-contained command/event multiplexer with per-request replies, connection pooling, dialog generations, and an existing-profile method policy. It passed real loopback WebSocket tests outside CUA. Browser binding, DOM snapshots, OOPIF management, endpoint discovery, profile consent, and input translation are separate modules. Copying the transport does not implement those capabilities.

### Modules that need adapters

Native AT-SPI is valuable code but not a standalone module as checked in. `atspi/native.rs` calls Linux window discovery, X11 popup handling, compositor-specific metadata, browser identity, and input functions. `atspi/snapshot.rs` uses the shared SnapshotStore; that store uses CUA session/runtime ownership and ToolResult. These dependencies preserve identity and avoid selecting the wrong accessible window. Extract the tree walk and observed-object actions behind a Dojo window provider, or fork the Linux platform crate with a Niri adapter. Merely importing `native.rs` would leave unresolved platform dependencies. [AT-SPI native implementation](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua-driver/rust/crates/platform-linux/src/atspi/native.rs), [snapshot store](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua-driver/rust/crates/cua-driver-core/src/snapshot_store.rs).

The complete browser engine already has a `BrowserPlatform` trait. A Dojo implementation must classify processes, prove native window ownership, detect PID reuse, prove endpoint ownership, handle preparation, and supply exact geometry. Niri IPC already includes `id` and optional `pid`, so there is an identity source; missing tiled-window geometry remains a limitation in the current fork. This is a genuine adapter boundary, with substantial functionality reusable above it. [BrowserPlatform](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua-driver/rust/crates/cua-driver-core/src/browser/platform.rs), [Niri window metadata](../../vendor/niri/niri-ipc/src/lib.rs).

CUA's native `ext_screencopy.rs` has no internal platform module imports and implements standard Wayland image-copy capture. It is a plausible way to remove Dojo's grim subprocess dependency. The checked-in function captures the first advertised output, uses roundtrips inside nominal deadline loops, and does not supply Dojo's selected-output/region contract. Porting requires named-output selection, bounded event dispatch, pixel-format review, and preserving Dojo's geometry/mapping checks. It was inspected, not executed on Niri. [Native capture](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua-driver/rust/crates/platform-linux/src/wayland/ext_screencopy.rs).

Recording has explicit callbacks for screenshots, accessibility snapshots, element positions, and click markers, so Dojo can supply those. The complete recorder also uses CUA session bookkeeping, action records, and global OnceLock hooks. Reuse the formats and recorder through a wrapper, or extract it as a coherent subsystem; it is not a one-file import. [Recording callbacks](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua-driver/rust/crates/cua-driver-core/src/recording.rs).

The optional `cua-perception` worker is an independent process with a bounded length-prefixed protocol. It accepts local images and model/runtime paths, so Dojo can call it without CUA's desktop driver. Its worker source inherits MIT, but the shipped icon detector is AGPL and model/runtime artifacts have separate notices. Source portability does not imply that the deployed model bundle is MIT. No model artifacts were downloaded or inference tested. [Worker](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua-driver/rust/crates/cua-perception/src/lib.rs), [model notices](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua-driver/rust/crates/cua-perception/models/THIRD_PARTY_NOTICES.md).

### Whole Driver embedding

The earlier statement that CUA has no integration hook was too broad. `DriverHostOptions` exposes `register_host_tools`, and ToolRegistry registers implementations of its public Tool trait. However, the SDK documents that hook as temporary compatibility for daemon administrative tools and says desktop operations belong behind the typed SDK contract. Runtime construction still selects `platform_linux` directly. This is not a supported replace-the-input-backend API. A custom core registry can host Dojo tools, but would import CUA policy/session/recording behavior and require checking schema/typed SDK consistency. [Host options](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua-driver/rust/crates/cua-driver-sdk/src/lib.rs), [runtime construction](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua-driver/rust/crates/cua-driver-sdk/src/runtime.rs), [ToolRegistry](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua-driver/rust/crates/cua-driver-core/src/tool.rs).

Embedding the whole SDK also introduces CUA's one-active-runtime restriction and process-global callbacks alongside Dojo's existing shared input service. The Linux crate includes X11, AT-SPI, native Wayland, cursor-overlay, and PiP dependencies. `cursor-overlay` itself depends on Driver core and contract, although its motion math is already separated. Copying the overlay therefore imports more infrastructure than copying motion/effects and rendering them in Dojo. [Linux dependencies](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua-driver/rust/crates/platform-linux/Cargo.toml), [overlay dependencies](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua-driver/rust/crates/cursor-overlay/Cargo.toml).

### Driver extraction verification

The rerunnable extraction probe is [probe.py](../../.scratch/cua-portability/probe.py). It checks the source revision, copies unchanged implementation files, creates standalone Cargo manifests, and verifies copied bytes. Generated sources and build outputs stay in `/tmp/dojo-cua-probe`.

```sh
python3 .scratch/cua-portability/probe.py /tmp/dojo-cua-portability /tmp/dojo-cua-probe
devenv shell -- cargo test --manifest-path /tmp/dojo-cua-probe/motion/Cargo.toml --all-features
devenv shell -- cargo test --manifest-path /tmp/dojo-cua-probe/helpers/Cargo.toml
```

The motion crate passed 14 unit tests, two integration tests, and three documentation tests. The standalone helper crate passed 48 tests across capture storage/admission, coordinate mapping, image conversion, browser coverage metadata, and CDP command/event routing. These tests prove independent extraction and preserved upstream behavior. They do not prove integrated Dojo actions, real-browser compatibility, AT-SPI delivery, or model inference. One unused-method warning remains because a crate-private perception helper has no caller in the extraction.

There is no defensible whole-repository percentage for portability. Generated language bindings, retired packages, platform runtimes, model artifacts, and app code do not share a useful denominator. The proven result is two whole crates, the motion and transcript crates, plus five Driver production modules copied unchanged, with concrete adapter work identified for the larger systems.
