# Wallpaper-derived desktop themes: target contracts

Research date: **2026-10-09**. Research only: no installation, application launch/restart, desktop change, or configuration edit. Read root `AGENTS.md`, `GLOSSARY.md`, `docs/agents/domain.md`, the existing [Omarchy/Aether report](omarchy-aether-theme-compatibility.md), and relevant [launcher research](dojo-launcher-research.md). No ADRs were present. Local source is work in progress, not a release baseline. This report **does not define Dojo's future schema or palette vocabulary**.

## Decision summary

**Current scope:** Dojo, Zen/Firefox, Neovim, T3 Code, Zed, Kitty, Ghostty, Yazi, Pi coding agent, OpenCode, GTK and Qt. **Claude and Codex are dropped** and are not requirements or blockers in this report.

**Hard requirement: every running target except Neovim must update on a theme change, with no restart/relaunch and no HM rebuild.** Neovim is explicitly exempt from 100% live reload: supply a dedicated Dojo colorscheme receiving generated colors, with application/reload behavior at least matching Omarchy. Startup-only resources and changes affecting only new windows/processes do not satisfy the other targets. Mode switching alone does not demonstrate arbitrary palette live updating. One-time setup remains separate and is **not authorized** by this research.

The proposed **extraction → semantic derived palette → application-specific exporters** architecture is sound, with HM owning stable configuration and darkman owning mode. Follow-up source inspection establishes practical live routes for **OpenCode V2, qtct-backed Qt Widgets, and named GTK themes**, not just mode switching. Full coverage of libadwaita, application-owned/QML colors and sandboxed consumers remains conditional. Extraction already exists; extraction is not application. Start with **all Dojo shell surfaces, Kitty, and Ghostty**, then the supplied Neovim colorscheme. Preserve every remaining target rather than substituting restart-based adapters.

Important discoveries:

- **T3 Code, Pi, and OpenCode V2 have real custom-theme formats.** Installed OpenCode's pinned source handles SIGUSR2 refresh and V1 theme migration; TokyoNight's V1 exporter can therefore work on this V2 build. Pi's installed package remains unidentified, while inspected upstream package metadata says `@earendil-works/pi-coding-agent` **1.1.0**. [T1–T5][P1][O3][TN3]
- **Zen needs a deliberate browser integration.** A supported Firefox theme extension gives live browser-theme updates, but Zen-specific workspace surfaces can require a small CSS bridge. Existing profile customization must not be replaced. Omarchy itself does not currently theme Firefox/Zen; community integrations do. [B1–B5]
- **GTK3, ordinary GTK4, and libadwaita are different targets.** Supported libadwaita integration is appearance/accent/high contrast, not arbitrary whole-desktop palette substitution. Global CSS overrides are possible but are a separate, fragile opt-in contract. [G1–G5]
- **Qt5/Qt6 need matching integration plugins.** qtct watches its config directory and reapplies palettes to existing processes; deliberately triggering that directory watcher is the missing publication step. Kvantum SVG reload is a separate unverified contract. `QT_QPA_PLATFORMTHEME` selects one authority, not three. [Q1–Q5][QT1–QT3]
- **A single active-generation symlink is not sufficient for every consumer. T3 rejects symlinked theme files.** Publish atomically replaced regular files into its watched directory; don't blindly HM-link its JSON from the store. [T2]

## Per-target matrix

Paths use the normal Linux home/XDG defaults; honor app-specific overrides. “HM wiring” is a **recommendation**, not a change made by this research. Restart-only behavior is a **noncompliant contract/blocker**, never an acceptable fallback or authorization to close applications.

### Live-update gate — authoritative acceptance assessment

Grades describe primary-source evidence, **not runtime tests on this machine**: **Pass** = existing-instance palette-update mechanism established; **Conditional** = viable source-backed bridge or prerequisite still needed; **Unverified** = no established end-to-end arbitrary-palette live path; **Fail** = demonstrated contract/scope is insufficient. Every target remains required. A setup-time activation/plugin enablement is distinct from per-theme application, but must be agreed explicitly; it cannot be disguised as a theme-change restart.

## Follow-up: actual Omarchy generation → publication → running-process update

This section supersedes earlier **docs-only** doubts about OpenCode and Qt and distinguishes **Omarchy core** from community theme hooks. Inspected core `omarchy-theme-set` stages files, calls `omarchy-theme-set-templates`, publishes current output, sends shell IPC, then runs app hooks in parallel and finally `omarchy-hook theme-set`. A script called `restart-*` is **not necessarily a restart**: inspect its body. Terminal/OpenCode scripts send reload signals; other hooks may really restart processes. [OM1–OM3]

### GTK: preserve the supported settings mechanism, change the publication seam

**Verified toolkit mechanics:** GTK3 and GTK4 `GtkSettings` handle `gtk-theme-name` change by calling `settings_update_theme`, which loads the **named theme provider**. Separately, their user `gtk.css` provider is initialized behind a static one-time guard. Changing a theme name **does not re-read that separate user stylesheet**. Thus the community's temporary-name flip has a real settings/notification basis, but does not prove its freshly copied global `gtk.css` loaded into all existing apps; its explicit restart fallback is significant evidence. [GTK1][GTK2][TH1]

**Practical proposal (not implemented):** publish a complete coherent generated GTK3/GTK4 named theme in writable XDG data, using generation-unique name or verified A/B provider names; put palette-dependent CSS in that provider, not only in global user imports. Once files exist, set the **desktop theme preference** to the new name. Existing applications receiving that preference load the new provider and repaint. Distinct names avoid same-value no-op and stale-file assumptions; no portal kill/app restart is part of the proposal. HM owns stable base/configuration/integration packages; generated names/assets and runtime selected state remain mutable. Existing user CSS can override it and needs a deliberate non-destructive policy.

On GTK4 Wayland the source maps `org.gnome.desktop.interface gtk-theme` to `gtk-theme-name`, propagates GSettings/portal changes, and can read portal settings instead of native settings. **Niri/darkman changes the path:** local Settings portal selects darkman, whose documented standardized export is mode—not the GNOME `gtk-theme` key. Portal-routed/sandboxed clients may not receive the generated name or see host theme assets. Don't change mode authority or run another portal service blindly; verify consumer routing, and if needed use a consciously designed Settings backend providing both darkman's mode and GTK theme preferences. This is a backend/integration question, not a reason to dismiss native non-sandbox GSettings notifications. [GTK3][L1][D3]

**libadwaita distinction:** inspected StyleManager sets GTK theme to **`Adwaita-empty`** unless `GTK_THEME`/Granite special path applies, and loads its **own resource/CSS providers**. It updates own providers for scheme, contrast, accent and fonts. Named third-party GTK themes therefore don't automatically replace libadwaita's palette. Global CSS can override some properties, but fresh file copies do not supply a universal live notifier; `GTK_THEME` forcing isn't an endorsed substitute for a desktop palette API. Supported scheme/accent is live; complete arbitrary palette across every libadwaita app remains a coverage blocker requiring cooperation or a proven supported extension, not a restart workaround. [GTK4]

### Qt: a concrete live qtct adapter exists

**qt6ct source:** construction queues `createFSWatcher` when desktop settings are enabled and QtWidgets support is compiled. Watcher observes **`Qt6CT::configPath()`**, **not** the selected colors file. Directory events debounce for **3000 ms**, then `updateSettings()` calls `readSettings()` and `applySettings()`. Read loads `[Appearance] color_scheme_path` when `custom_palette=true`; apply sets application palette and sends ThemeChange/setPalette to existing widgets. It also avoids overriding an initially application-owned palette (`AA_SetPalette`), and has ignored-app/desktop-settings-aware checks. **qt5ct archived source has the equivalent directory-watch/3000 ms/update/palette chain**; prove current packaged Qt5 parity before implementing. [QT1][QT2]

**Recommended qtct seam:** declaratively provision correct ABI plugin and stable per-app platform-theme selection once; use stable HM-owned qtct config with `custom_palette=true`, a generated scheme path, and a palette-respecting style such as **Fusion**. Per theme: atomically publish validated scheme, then atomically replace a dedicated harmless marker **in top-level `~/.config/qt5ct` / `qt6ct`**, creating a directory event. This leaves HM config untouched yet causes running plugin to reread its referenced scheme. Palette under a `colors/` subdirectory alone may not trigger a watcher on its parent. Marker bridge follows source's directory event behavior; actual OS/plugin delivery, installed packages and acceptable three-second latency need isolated validation. No restart, D-Bus signal or settings-file rewrite is required for this qtct route.

Keep each qtct **parent directory writable**, not an HM-linked whole store directory. Individual stable config symlinks are compatible with a mutable sibling marker; detect preexisting directory ownership before setup. Similarly do not declaratively freeze the runtime GTK theme-name selection to one generation: stable HM integration and mutable selected theme are separate authorities. The coordinator mirrors darkman's mode while choosing generated colors; it does not let GNOME/Qt mode setters become competing schedulers.

**KDE alternative:** Qt5/Qt6 plasma-integration listens on session D-Bus **`/KGlobalSettings`, `org.kde.KGlobalSettings`, `notifyChange(int,int)`**. PaletteChanged reparses KDE configuration, reloads KColorScheme and updates QApplication/QGuiApplication palettes; Qt6 explicitly emits `paletteChanged` for Qt Quick `SystemPalette` consumers and sends ApplicationPaletteChange. Apps specifying `KDE_COLOR_SCHEME_PATH` can opt out. A KDE stack can therefore provide real live palette change, but requires the matching framework/platform integration and correct notification enum/tool/config owner—not copying arbitrary qtct INI into `kdeglobals`. This path is **not used by inspected Omarchy core/THPM**, and is an alternative to qtct, not an extra conflicting `QT_QPA_PLATFORMTHEME`. [QT4]

**Kvantum:** requires matching Qt5/Qt6 style build and authored `.kvconfig`/SVG assets; Qtct applies QPalette and theme events but this does not establish that Kvantum reparses changed SVG/custom graphic colors. Inspected Kvantum style/manager code did not establish a universal external theme-file watcher. Keep SVG/resource reload **unverified** rather than attributing qtct's proven palette watcher to Kvantum. Qt Quick custom materials/app stylesheets are also outside generic QWidget palettes. [QT5]

## Zen: recommended seam and Omarchy comparison

### Supported browser theme versus profile CSS

Mozilla's `browser.theme.update(Theme)` requires the **`theme` permission**, accepts a theme object, and updates all windows unless a window ID is provided. The object has browser UI `colors`, optional `images`, and `properties`; `color_scheme`/`content_color_scheme` describe appearance. A static WebExtension theme is packaged in `manifest.json`; a dynamic extension can receive new palette data and call the API. This is **not** a host CSS include, and a theme extension is not allowed to read arbitrary home files directly. A native-messaging helper, explicit local data bridge, or extension-controlled import is needed for generated desktop data. Restore a selected/generated theme on browser startup; runtime `theme.update` is not by itself persistent desktop state. [B1][B2]

Browser theme colors do not recolor arbitrary websites. `userContent.css` can target browser internal/new-tab pages or chosen content, but is a separate styling surface, with privacy/accessibility implications. `userChrome.css` targets browser chrome and can reach Zen-specific surfaces that lightweight themes do not. Zen documents the `chrome/userChrome.css` path and enabling `toolkit.legacyUserProfileCustomizations.stylesheets`; its Browser Toolbox live-edit guide **does not establish automatic reload of external generator edits** in ordinary running browser sessions. Startup-loaded CSS changes should be described as restart-required unless a real extension/live bridge supplies dynamic values. [B3]

Recommended design: a **small stable, trusted extension + optional stable Zen CSS bridge**, with palette values updated through the browser theme API. HM can own the packaged extension/native host manifest and an agreed stable stylesheet/import, while Dojo owns only a dedicated mutable palette payload. Profile discovery/setup must be explicit and preserve the user's existing Zen Mods, imports, workspace theming, and policy-installed extensions. Do not HM-own or replace an entire profile; do not routinely rewrite `prefs.js`. Exact native-messaging manifest search path for this **Nix-wrapped Zen build remains unverified**; test the wrapper/Gecko lookup rather than assuming Firefox and Zen use identical directories.

### What “Omarchy Firefox generation” actually supplies

- **First-party Omarchy:** inspected `omarchy-theme-set-browser` writes Chromium-family managed policies, not Firefox/Zen themes. Its Firefox policies file is defaults, not a generated palette. No first-party Firefox palette exporter appears in this snapshot. [B4]
- **`VannRR/omarchy-firefox-theme`:** a community extension/native helper. `createFirefoxTheme(r,g,b)` takes **one RGB source color**, derives Chromium-like/Material colors, infers dark/light from that color, and returns a Firefox theme object. Native helper watches the older `~/.config/omarchy/current/theme/chromium.theme` location. Useful generation precedent, **not exact preservation of the full wallpaper-derived palette**, not a darkman mode authority, and not evidence that every Zen workspace surface is covered. Importing its active-path assumptions would regress the current state/config split. [B5]
- **`cover/omafox`:** newer community integration specifically documents **Firefox and Zen**, full Omarchy palette mapping, Linux native messaging/inotify of `~/.local/state/omafox/theme.json`, saved extension state, and a Zen bridge at `chrome/omafox.css` imported from `userChrome.css`. Sets `toolkit.legacyUserProfileCustomizations.stylesheets` and `zen.theme.disable-lightweight`; first setup needs one restart. Its marked blocks preserve other customization, and it refuses unrelated existing bridge files. This is the closest demonstrated **live theme API + stable Zen CSS** precedent. It depends on Omarchy 4 and its command/hooks, so Dojo should borrow the seam, not run `omafox setup` as an unreviewed installer. Its README excludes Flatpak Zen. [B6]

Clarify which “Firefox gen” project the user meant; these implementations differ substantially. The VannRR generator is plausible, but it must not be silently attributed to Omarchy core.

## Mode authority, portals, and ownership

### One authoritative mode, several propagation paths

Local HM enables darkman (`portal=true`, `usegeoclue=false`), maps `org.freedesktop.impl.portal.Settings=darkman` in `niri-portals.conf`, and binds Niri's toggle to `darkman toggle`. Keep this. Do not replace the current portal selection with upstream Niri defaults accidentally; retain GNOME ScreenCast/Screenshot and GTK fallback. [L1][D1]

**Correction to the earlier report's uncertainty:** installed darkman 2.3.1 documentation confirms a **Unix socket** at `$XDG_RUNTIME_DIR/darkman/control.sock`, commands `get`, `set light|dark`, `toggle`, and socket command **`watch`**, which immediately returns current mode then each transition. CLI subcommands listed are `run`, `set`, `get`, `toggle`; don't invent `darkman watch` as a CLI command. Mode hooks under `$XDG_DATA_HOME/darkman` and XDG data dirs receive `light`/`dark` as `$1`; legacy dark/light-mode directories still work. Current portal is a D-Bus integration, but **do not assume a historical darkman custom D-Bus control API remains the correct native control seam**. [L4][D2]

Suggested responsibilities (not implementation):

1. Mode UI calls darkman to change mode; Dojo observes socket mode or receives one central mode hook.
2. The single theme application coordinator selects the correct derived light/dark generation and publishes fragments.
3. The same coordinator mirrors appearance to settings needed by non-portal GTK consumers. No independent GTK/Qt/terminal scheduler.
4. GUI apps following the portal and terminal apps following terminal appearance should converge on that mode. Test the chain: darkman → portal/GTK → Ghostty and explicit Kitty palette → OpenCode/Pi/Yazi. **Terminal appearance detection is indirect and version-dependent**, not an automatic direct darkman connection.

The Settings portal standard exports color scheme `0=no preference`, `1=dark`, `2=light`, and optional RGB accent/contrast preferences; it is **read-only to applications**, not a palette distribution API. darkman documents its color-scheme implementation, **not an arbitrary accent exporter**. Choosing darkman for the whole Settings interface can mean a GNOME accent key does not reach portal consumers; don't assume a backend fallback merges all keys. Investigate whether the installed backend exposes accent before promising it, or defer accent to a consciously chosen future integration. [D2][D3]

No location was configured in the inspected HM darkman settings and GeoClue guessing is disabled. darkman's manual says **without a known location, automatic sunrise/sunset transitions are disabled**. Manual toggling still works; no request to infer location or enable scheduling is made here. Startup convergence should explicitly query current mode rather than depend on a transition occurring after Dojo launches. [L1][L4]
