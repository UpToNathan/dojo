# Which CUA components fit Dojo

Inspected 2026-10-13 against CUA `88aff7e5424e9ed45b93ded85eb4111472ca5190` and current Dojo source. This is a source audit. It adds no runtime evidence and ran no tests, UI, installs, or artifact downloads.

## Scope correction

Dojo needs an assistant operating its existing Niri desktop. Pi owns durable tasks and conversations; pi-ai owns provider requests and credentials. Execution is Rust. VMs, QEMU, cloud sandboxes, production Python, whole-desktop capture spanning monitors, and a separate durable approval store are outside this scope.

The old [portability report](cua-system-portability.md), [adoption spec](../../.scratch/cua-adoption/spec.md), and [import README](../../vendor/cua/README.md) mix useful component extraction with whole-product parity. In particular, the spec makes sandbox/remote tickets mandatory for full parity. That requirement no longer describes the user's goal. Copying the SDK or registering a schema does not make its product relevant or its behavior integrated.

CUA has useful independent layers. The [SDK workspace](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua/Cargo.toml) includes many products beyond local desktop execution. Select by the operation Dojo needs, then retain the smallest coherent upstream implementation and its tests.

## Duplicated responsibilities and unrelated products

Dojo should keep Pi's scheduler, canonical transcript, budget enforcement and provider transport. CUA's Python autonomous loops, agent supervisors, provider credential handling, session orchestration and ambient Driver batch/replay execution duplicate these responsibilities. Useful pure decoders and projections can remain extracted. The [retired Python agent](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/python/agent/cua_agent/agent.py) is not a production dependency for this architecture. The upstream [PII callback](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/python/agent/cua_agent/callbacks/pii_anonymization.py) is not evidence of a working redactor.

VM/container/cloud sandbox lifecycle, images, Fleet, Lume, guest daemon/relay, Spaces sharing, Keyvault, Teleport, shared volumes and remote media/viewer products solve other product requirements. None is needed to operate this host. Their existing copied source can remain inert until removed or justified, but none belongs in the completion checklist. The optional [CUA resource extension](../../tools/speech/cua-extension.mjs) is a sandbox/Spaces client and is distinct from the integrated Driver. [VMM manifest](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/libs/cua/crates/cua-vmm/Cargo.toml), [license/product map](https://github.com/trycua/cua/blob/88aff7e5424e9ed45b93ded85eb4111472ca5190/LICENSING.md).

Driver's internal session handles, capture ownership and child cleanup remain necessary within Dojo's service. These execution lifetimes are distinct from an independent agent task scheduler or another durable conversation database.

CUA's cursor overlay also duplicates Niri's independent agent cursor. Retain useful motion mathematics already adapted by Dojo; do not start a second cursor UI just to match upstream behavior. Windows/macOS platform implementations are references, not Linux deployment targets. Driver permissions/grants should integrate with Dojo's existing task authorization rather than establish another durable approval owner.

## Recommended order

1. Replace the broad parity checklist with local task capabilities. Record implemented routes, refused routes, and exact live evidence separately from copied source.
2. Maintain the chosen Helium/browser-control route and its cancellation and uncertainty checks. The copied CUA browser route is retired.
3. Native accessibility binding is settled: GTK, Qt5, Qt6, GPUI and generic-annotation producers have exact binding and semantic actions. Chromium/Electron is deliberately OCR/vision only and is not patched. Further toolkits need a producer that publishes an exact surface-to-root identity.
4. Extend missing native Driver actions only when a target task requires them. Reuse original handlers while routing through the shared native seat; Unicode/layout-safe text and drag are likely task-driven candidates.
5. Use existing verification and trace export to build a small repeatable local task corpus. This identifies failures worth fixing and gives perception/model additions a measurable reason. The [corpus and runner](../task-corpus.md) exist; real-agent pass rates are not yet measured.
6. Add perception or a specialist model only if that corpus demonstrates gaps in ordinary screenshot/DOM/AT-SPI operation. Setup, transcript and icon code already have bounded uses and should grow with corresponding Dojo features.

This order is a source-informed recommendation, not a measured performance ranking. The relevant target is reliable local assistant tasks.
